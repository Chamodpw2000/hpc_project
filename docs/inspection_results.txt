Abstract
This project implements and analyzes the PageRank algorithm using multiple High Per-
formance Computing (HPC) programming models. PageRank is an iterative graph al-
gorithm used to estimate the relative importance of nodes in a directed graph. In this
project, the algorithm is applied to real-world graph datasets such as social networks and
web graphs in order to identify influential nodes.
The implementation begins with a serial CPU version, which is used as the base-
line for both accuracy and performance comparison.
The project then extends the
computation using shared-memory programming with OpenMP and POSIX Threads,
distributed-memory programming with MPI, GPU acceleration with CUDA, and two
hybrid approaches: MPI + OpenMP and MPI + CUDA. The correctness of each imple-
mentation is verified by comparing its output with the serial output using Root Mean
Square Error (RMSE). Performance is analyzed using execution time, speedup, efficiency,
and scalability across different datasets and parallel configurations.
The experimental results show that all tested parallel and hybrid implementations
produce PageRank values very close to the serial baseline. The PageRank sum remains
approximately 1.000000, and RMSE values are close to zero. The CUDA implementa-
tion provides performance improvement for some larger datasets, while MPI and hybrid
implementations show that speedup depends strongly on problem size, communication
overhead, hardware availability, and graph structure. In particular, the MPI + CUDA
implementation is designed for multi-GPU environments, but was tested on a single-GPU
laptop, which limits its full performance potential.

1.1
Project Overview
The aim of this project is to parallelize the PageRank algorithm using different HPC
programming paradigms and analyze their correctness and performance. PageRank is
suitable for parallel computing because the rank value of each node can be updated
independently during each iteration once the previous iteration’s rank vector is available.
The project includes the following implementations:
• Serial PageRank implementation
• OpenMP shared-memory implementation
• POSIX Threads shared-memory implementation
• MPI distributed-memory implementation
• CUDA GPU implementation
• Hybrid MPI + OpenMP implementation
• Hybrid MPI + CUDA implementation
The same graph input datasets are used across implementations so that execution
time, speedup, efficiency, and accuracy can be compared fairly.
1.2
PageRank Algorithm
PageRank assigns an importance score to each node in a directed graph. A node receives
a higher PageRank value if many nodes point to it or if it receives links from other
important nodes.
Therefore, PageRank is not only a simple in-degree count; it also
considers the importance of the nodes providing incoming links.
For a graph with N nodes, the PageRank of node i is calculated as:

iteratively until the global change between two consecutive iterations becomes smaller
than the tolerance value or the maximum number of iterations is reached.
In this project:
• Damping factor: 0.85
• Maximum iterations: 50
• Convergence tolerance: 10−6
1.3
Graph Representation
The input graph is read from a text file where each line contains a directed edge:
source destination
For example, 0 1 means that node 0 has a directed edge to node 1.
The graph is stored using an incoming-edge structure similar to Compressed Sparse
Column (CSC) representation. The main arrays are:
• src: stores source nodes of edges
• dst: stores destination nodes of edges
• outDegree: stores number of outgoing edges for each node
• inEdges: stores incoming source nodes for each destination node
• inPtr: stores pointer offsets for incoming edges of each node
This representation is efficient for PageRank because the rank of a node depends on
its incoming edges.

1.5
Serial Implementation
The serial implementation runs on a single CPU core and is used as the baseline. It
initializes all PageRank values equally and repeatedly updates each node’s rank using
the PageRank formula. The serial version also calculates dangling-node contribution and
convergence difference in a sequential manner.
The serial implementation is important because:
• It provides the reference output for accuracy comparison.
• It provides the baseline execution time for speedup calculation.
• It helps verify whether the parallel implementations produce correct results.
1.6
OpenMP Implementation
The OpenMP implementation uses shared-memory parallel programming.
The main
PageRank loops are parallelized using #pragma omp parallel for. OpenMP automat-
ically manages thread creation, scheduling, and synchronization.
The following operations are parallelized:
• Initializing PageRank values
• Calculating dangling-node contribution using reduction
• Updating PageRank values for all nodes
• Computing convergence difference using reduction
5


--- PAGE 7 ---
OpenMP is suitable for multi-core CPUs because all threads share the same memory
space. However, synchronization and reduction operations can introduce overhead.
1.7
POSIX Threads Implementation
The POSIX Threads implementation uses manual thread management. The total set
of nodes is divided among threads, and each thread computes PageRank values for its
assigned node range. Compared with OpenMP, Pthreads requires explicit thread creation,
workload division, joining, and synchronization.
Key characteristics of the Pthreads implementation are:
• Explicit control over thread creation and node partitioning
• Shared-memory parallel execution
• Manual synchronization where shared values are updated
• More implementation complexity than OpenMP
Pthreads provides a lower-level understanding of shared-memory parallelism compared
with OpenMP.
1.8
MPI Implementation
The MPI implementation uses distributed-memory programming.
Multiple MPI pro-
cesses are created, and the graph nodes are divided among those processes. Each process
computes PageRank values only for its assigned node block.
The workflow is:
1. Process 0 reads the graph from the dataset.
2. Process 0 broadcasts the full graph data to all MPI processes using MPI Bcast.
3. Nodes are divided among MPI processes.
4. Each process computes new PageRank values for its assigned nodes.
5. MPI Allreduce is used to calculate global dangling-node contribution.
6. MPI Allreduce is used to calculate global convergence difference.
7. MPI Allgatherv is used to share updated PageRank values among all processes.
8. Process 0 prints and saves the final output.
MPI is useful for distributed systems and multi-node execution, but communication
overhead can reduce speedup for small datasets or high process counts.

1.9
CUDA Implementation
The CUDA implementation uses GPU acceleration. The CPU loads the graph and copies
the required arrays to GPU memory. CUDA kernels are launched so that GPU threads
compute PageRank values in parallel.
The CUDA design uses:
• One GPU thread for one graph node
• CUDA kernels for dangling-node calculation
• CUDA kernels for PageRank update
• CUDA kernels for convergence difference calculation
• CUDA block sizes such as 128, 256, and 512
CUDA can provide high parallelism because thousands of GPU threads can execute
concurrently. However, performance depends on dataset size, memory transfer overhead,
atomic operations, GPU occupancy, and graph memory access patterns.
1.10
Hybrid MPI + OpenMP Implementation
The first hybrid implementation combines MPI and OpenMP. MPI is used to divide the
graph among processes, while OpenMP is used inside each MPI process to parallelize the
computation over CPU threads.
The model is:
MPI processes × OpenMP threads per process
For example:
2 MPI processes × 2 OpenMP threads = 4 total workers
The workflow is:
1. MPI distributes node ranges among processes.
2. Each MPI process uses OpenMP threads to compute PageRank for its local node
range.
3. MPI collective operations combine global dangling sum and convergence difference.
4. MPI shares updated PageRank blocks after each iteration.
This hybrid method combines distributed-memory and shared-memory parallelism.
It is suitable for systems where each node has multiple CPU cores.

1.11
Hybrid MPI + CUDA Implementation
The second hybrid implementation combines MPI and CUDA. MPI distributes node
partitions among processes, while CUDA performs the PageRank computation on the
GPU for each process’s assigned node range.
The MPI + CUDA workflow is:
1. MPI divides graph nodes among processes.
2. Each MPI process is intended to use one dedicated GPU.
3. CUDA kernels compute dangling-node contribution, PageRank updates, and con-
vergence difference.
4. MPI collective operations exchange global information between processes.
5. Final PageRank values are gathered and compared with serial output.
The implementation also uses CUDA streams to divide each local node partition into
multiple stream segments. This is intended to increase intra-GPU parallelism.
In the available test environment, only one CUDA-capable GPU was available. There-
fore, the MPI + CUDA implementation was tested using one MPI process. This validates
correctness, but does not fully demonstrate the scalability potential of MPI + CUDA on
a multi-GPU system. On a multi-GPU cluster, the expected mapping would be:
MPI Rank 0 →GPU 0,
MPI Rank 1 →GPU 1,
MPI Rank 2 →GPU 2

3.8
Performance Discussion
The results show that parallel performance depends on the relationship between compu-
tation workload and overhead.
For small datasets, parallel implementations can be slower because the overhead of
creating threads, launching kernels, transferring data, and communicating between pro-
cesses is larger than the computation itself. This is clearly visible in the sample graph
and soc-Epinions1 CUDA results.
For larger datasets such as web-Google and WikiTalk, CUDA begins to show per-
formance benefits because there is more parallel work available for the GPU. However,
13


--- PAGE 15 ---
graph algorithms such as PageRank have irregular memory access patterns, and some
nodes may have many more incoming edges than others. This causes load imbalance
among threads and reduces the achievable speedup.
MPI performance is affected by communication overhead. In PageRank, updated rank
values must be shared after each iteration. Therefore, operations such as MPI Allgatherv
can become expensive, especially for large graphs.
Hybrid MPI + OpenMP performs well when the number of total workers matches the
available CPU resources. However, oversubscription reduces efficiency. Hybrid MPI +
CUDA is conceptually strong for multi-GPU systems, but cannot show full potential on
a single-GPU laptop.

Chapter 5
Conclusion
This project successfully implemented and analyzed the PageRank algorithm using several
HPC programming models. The serial implementation served as the baseline for both
correctness and performance comparison. OpenMP and Pthreads demonstrated shared-
memory parallelism on CPU cores. MPI demonstrated distributed-memory parallelism
using multiple processes. CUDA demonstrated GPU acceleration. Two hybrid methods,
MPI + OpenMP and MPI + CUDA, were also implemented to combine multiple parallel
programming models.
The accuracy analysis showed that all tested parallel and hybrid implementations
produced results very close to the serial implementation. RMSE values were close to zero
and the total PageRank sum remained approximately 1.000000, confirming correctness.
The performance analysis showed that parallel speedup depends on dataset size, graph
structure, hardware resources, and communication overhead. MPI achieved speedup with
4 processes but degraded with oversubscription. CUDA achieved speedup for some larger
datasets, especially web-Google, but was slower for smaller or irregular datasets. Hybrid
MPI + OpenMP achieved speedup when the number of workers matched the available
CPU resources. Hybrid MPI + CUDA produced correct results but was limited by the
single-GPU testing environment.
Overall, the project demonstrates how the same graph algorithm can be mapped to
different HPC paradigms and how performance depends not only on parallelism but also
on communication, synchronization, memory access, and hardware availability.

1.1
Project Overview
This project develops and evaluates a high-performance Student Marks Analytics
Engine (named Swiftcore) designed to compute complex statistics and subject relationships
from large student databases.
The system features:
 Frontend: A Next.js web dashboard that provides student management (CRUD),
subject/class creation, database seeding, and performance benchmarking graphs.
 Backend: A C-based API server using the CivetWeb library that connects to
MongoDB Atlas using the MongoDB C Driver (libmongoc).
 Compute Engine: Parallel statistical algorithms written in C, utilizing OpenMP,
POSIX Threads (pthreads), and MPI.
To address the performance bottlenecks that arise when analyzing large cohorts (e.g.,
tens of thousands of students across multiple subjects), the backend compute engine is
parallelized using three different High Performance Computing (HPC) paradigms: shared-
memory programming with OpenMP, manual low-level shared-memory programming with
POSIX Threads (pthreads), and distributed-memory programming with the Message
Passing Interface (MPI).
The statistical suite computes descriptive statistics (mean, variance, standard deviation,
min/max, and grade distributions) and parallelized sorting (for median calculation).
Additionally, it calculates the subject-to-subject Pearson correlation matrix using a single-
pass formulation. Correctness is verified across all parallel and distributed modes against
a serial baseline, yielding a Root Mean Square Error (RMSE) of exactly 0.0. Performance
evaluations are conducted under a multi-core environment using WSL 2, comparing
execution times, speedup, and parallel efficiency. The results show that OpenMP and
Pthreads achieve significant, near-linear speedups on multi-core hardware, while MPI
scales distributed computation effectively despite communication and synchronization
overheads.

Since the calculations for individual students, subjects, or subject pairs are largely

2.3.1
Application of Parallel Programming Concepts
To accelerate the statistical calculations over large-scale marks matrices, three distinct
high-performance computing models are implemented:
1. Loop-Level and Task-Based Shared Memory (OpenMP): The computation
of descriptive statistics (sums, min, max, grade distribution) utilizes fork-join
parallelism. The data loops are split among threads using #pragma omp parallel
for directives combined with reduction clauses (reduction(+:p sum) and custom
reduction variables) to avoid data races. For the median calculation, a parallel merge
sort is implemented recursively; sub-arrays are sorted by spawning OpenMP tasks
(#pragma omp task) up to a recursion depth limit of 4, ensuring thread overhead is
kept to a minimum.
2. Low-Level Worker Thread Team and Merging (Pthreads): The Pthreads
implementation manages worker thread execution manually for granular control.
The workload of N student records is partitioned evenly into T chunks. A team of
threads is created: T threads compute local sums, minimums, maximums, and grade
distributions, while another T threads concurrently copy and sort their respective
chunks using the standard C library qsort. After a barrier join, a second phase
spawns T threads to compute local variance sums using the globally-reduced mean.
Finally, the sorted chunks are merged hierarchically using a pairwise merge algorithm
to determine the global median.
3. Distributed Memory Collective Communicators (MPI): To support dis-
tributed marks analysis across multiple compute nodes, an MPI-based master-worker

architecture is implemented. The master process (Rank 0) queries student records
from the database, broadcasts the array metadata using MPI Bcast, and scatters the
scores across rank communicators using MPI Scatterv. Worker processes compute
local aggregate statistics and reduce them back to Rank 0 using collective communi-
cation calls (MPI Reduce for minimums, maximums, sums, and grade counts). The
scores are then gathered back to Rank 0 using MPI Gatherv to perform the final
sort for median calculation.
A database seeding route (/api/seed) is provided to generate synthetic student profiles
with randomized scores using a uniform distribution to simulate realistic datasets. The
evaluations in this report are conducted on three dataset sizes:
 Small: N = 1, 000 students
 Medium: N = 10, 000 students
 Large: N = 50, 000 students
2.4
Serial Implementation
The serial implementation serves as the baseline. It runs on a single CPU core and
executes the statistical loops sequentially. Sorting is done using the standard C library
qsort.
2.5
OpenMP Implementation
OpenMP is utilized for loop-level shared-memory parallelization.
 Loop reductions accumulate statistics:
#pragma omp parallel for reduction(+:p_sum) \
reduction(min:p_min) reduction(max:p_max)
 The sorting step is parallelized recursively using OpenMP tasks:
#pragma omp task shared(arr) if(depth < 4)
parallel_merge_sort(arr, l, m, depth + 1);
2.6
POSIX Threads Implementation
Pthreads is used for manual, fine-grained thread control. The compute engine splits
the workload among T threads.
 Phase 1: Spawns 2T threads simultaneously. T threads calculate local statistics
(sum, min, max, grade counts), while another T threads copy and sort local chunks
of the score array.
 Phase 2: Spawns T threads to compute variance using the global mean calculated
in Phase 1.
 Merge: Hierarchically merges the sorted chunks pairwise to obtain the final sorted
array.

2.7
MPI Implementation
MPI is used to evaluate distributed-memory scalability. In distributed mode, multiple
processes (ranks) are initialized.
 Rank 0 (Master): Pulls data from MongoDB, broadcasts the size N using
MPI Bcast, scatters the scores to all ranks using MPI Scatterv, and participates in
reductions.
 Worker Ranks: Run a daemon loop (mpi worker loop) waiting for commands
from Rank 0. Upon receiving a calculate command, they receive their local chunk
of scores.
 Reductions: Ranks compute local stats and use MPI Reduce to aggregate sum,
min, max, variance, and grade distributions back to Rank 0.
 Gather: Local scores are gathered back to Rank 0 using MPI Gatherv to perform a
sequential qsort for median calculation.

4.6
Distributed Scaling and Communication Overhead
The MPI implementation suffers from communication overhead. In shared-memory
models, threads access the same memory buffer. In MPI, data must be copied and
transmitted across processes:
1. MPI Scatterv distributes the score array from Rank 0 to worker ranks.
2. MPI Reduce aggregates partial sums back to Rank 0.
3. MPI Gatherv gathers the entire array back to Rank 0 for sorting.
This communication overhead makes MPI less efficient for small or medium datasets on a
single machine. However, in a multi-node cluster with a distributed database, MPI allows
scaling to dataset sizes that exceed the memory of a single node.

5
Conclusion
This project successfully implemented and evaluated the Student Marks Analytics
Engine (Swiftcore) using multiple parallel programming paradigms. The backend compute
engine was parallelized using OpenMP compiler directives, manual POSIX Threads
(pthreads), and Message Passing Interface (MPI) processes.
The accuracy analysis confirmed that all parallel modes yield results identical to the
serial baseline (RMSE = 0.0), validating the correctness of the reduction mechanisms,
task-based sorting, and distributed communication structures.
Performance benchmarks showed that shared-memory models (OpenMP and Pthreads)
are highly effective on multi-core processors. OpenMP achieved a 3.29x speedup and
Pthreads achieved a 3.05x speedup for descriptive statistics on 4 threads. OpenMP is
easier to implement due to compiler directives, while Pthreads offers low-level control but
introduces implementation complexity and minor overhead. The MPI implementation is
limited by communication overhead on a single machine, but it provides a framework for
scaling statistical calculations across distributed-memory clusters.
Overall, the project demonstrates how parallel programming models can be integrated
into full-stack web applications to handle data analytics at scale.
